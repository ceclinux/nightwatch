# Nightwatch v0.6 "Night Watch": desktop widgets

Date: 2026-09-25
Status: built in v0.6.0
Owner: rsutcliffe
Design source: the widget mockups the owner approved on 25 September 2026 (design canvas "Nightwatch widget mockups"). The canvas shows small, medium and large widgets on a clear night, plus no-window, bright-night, stale-forecast and sources-disagree states.
Builds on: v0.5 (the agreement line) and the v0.4 design tokens.

## 1. Purpose

Answer "is tonight worth it?" at a glance on the desktop, without clicking. The widget is the first of three layers, each one step deeper than the one before (owner, 25 September 2026):

| Surface | Question | When |
|---|---|---|
| Widget | Is tonight worth it? | Seen on the desktop, no click |
| Popover | Why, and should I commit? | One click on the menu-bar star |
| Targets window | What exactly do I point at, and where from? | Planning the session |

Notifications stay the prompt that comes to you. The widget is the same answer, there whenever you look.

Success criteria:

1. Small, medium and large widgets match the mockups: the bezel, the verdict, the reason line, the Open-Meteo line, the bars and, on the large size, the best three targets and the update line.
2. The widget never fetches weather and never disagrees with the popover. It draws a snapshot the app writes after each patrol.
3. Clicking a widget opens the Targets window on tonight's targets. Clicking a large widget's target row opens that target.
4. The Command Line Tools build keeps working and ships the app without the widget. Only a build with Xcode adds it.
5. The four other states from the mockups appear when the snapshot calls for them: no window, bright night, a stale forecast (over six hours old) and sources disagreeing.

## 2. Decisions

| Topic | Decision |
|---|---|
| Sizes | Small, medium and large desktop widgets, as mocked. No extra-large |
| Data | After each patrol the app writes `widget.json` (§3) to a folder the widget can read, and asks WidgetKit to reload. The widget reads only that file |
| Shared look | The bezel, bars, warning dot and tokens move into a new SwiftPM library target, `NightwatchUI`, used by both the app and the widget. The widget and popover then cannot drift apart |
| Build | The widget extension needs an Xcode target. A committed `project.yml` (xcodegen) generates it, so no generated project file lives in the repo. `scripts/build-app.sh` builds the widget only when Xcode and xcodegen are present, and otherwise builds the app as today |
| Click | Opens the Targets window through the `nightwatch://targets` URL; a target row opens `nightwatch://target/<id>`. Confirmed by the spike (§4) |
| Refresh | The app reloads the widget after every patrol. The widget's own timeline asks again after 30 minutes, as a fallback |
| Stale | Over six hours old, the widget shows "Forecast N h old" with the amber dot, as mocked. The six hours are the same rule the alerts use |
| Colours | The v0.4 tokens, with red for clear sky only. The system draws the widget's container background, as widgets require |

## 3. The snapshot, `widget.json`

Written by `Store` after each plan is computed. It is a Codable `WidgetSnapshot` in SkyCore, so it can be tested. It carries only what the widget draws:

- the site name
- `fetchedAt`
- the score
- the plan mode
- the headline, window start and end, and hours
- the reason line (`Copy.heldBack`, or the no-window reason)
- the agreement text and whether it warns
- the 60 bezel slots
- the bars (hour, clear %, lit)
- up to three targets (catalogue ID, name or type, best time and altitude, target id)
- tomorrow's window, for the no-window state
- the notify time

It holds nothing the popover doesn't already show. Nothing is logged: each patrol replaces the file.

## 4. Unknowns to settle in a spike first (plan Task 1)

These need a throwaway build against the owner's Apple Developer account before any plan commits to an answer:

1. Whether a WidgetKit extension inside Nightwatch's app bundle, as a menu-bar agent app, shows in the macOS widget gallery. It must be signed with the team's certificate.
2. How app and widget share `widget.json`. Candidates are an App Group container, or the widget reading the app's cache under its sandbox rules. Also, whether the App Group must be registered in the developer portal and added to the App ID and profile. That is an owner step, as the WeatherKit capability was.
3. Whether a widget click can open a URL the app handles (`nightwatch://targets`, `nightwatch://target/<id>`), and what happens when the app is already running.
4. How `containerBackground` and Liquid Glass render a dark widget on macOS 26 and 27.

The spike needs the owner once: to add the widget from the desktop's widget gallery, and to report whether it appears.

### Spike results, 25 September 2026

The throwaway build ran outside the repo: a menu-bar-only app with a WidgetKit extension, bundle IDs `io.github.rsutcliffe.nwspike` and `.widget`, built with Xcode 27 and automatic signing. It was tested on the owner's Mac (macOS 27.0).

1. **Gallery: yes.** The widget of an agent (menu-bar-only) app appears in the desktop widget gallery under the app's name, in all three sizes. Desktop widgets were switched off on the owner's Mac (System Settings › Desktop & Dock › Widgets › Show widgets › On Desktop). That setting must be on to place one, so the README says so.
2. **Sharing: an App Group named with the team ID** (`8B44CZ9923.<bundle id>`), in both the app's and the sandboxed widget's entitlements. It needed no portal registration and created no new identifier or profile on the account. The app wrote `widget.json` into `~/Library/Group Containers/<group>/`, and the widget read it.
3. **Click-through: yes, both kinds.** Clicking the widget delivered `nwspike://targets` to the running app through `application(_:open:)`. A `Link` in the large widget delivered `nwspike://target/NGC7000`. The app must declare the URL scheme in `CFBundleURLTypes`.
4. **Look:** a dark `containerBackground` renders on the macOS 27 desktop as a dark, slightly translucent panel over the wallpaper. The system dims widgets when windows are in front (the owner can set "Dim widgets on desktop" to Never).
