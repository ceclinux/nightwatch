# Nightwatch v0.5 "The Fifth Elephant": forecast agreement

Date: 2026-09-25
Status: built in v0.5.0 (plan docs/plans/2026-09-25-v0.5-fifth-elephant.md)
Owner: rsutcliffe
Source: the Nightwatch Product Direction Synthesis, Direction A ("Confidence, not cloud cover"), as reshaped by its assumption challenge. The owner approved the direction on 25 September 2026: "Yes to the forecast agreement signal".
Builds on: the v0.1 to v0.4 specs. Behaviour not named here stays as those specs say.

## 1. Purpose

UK observers check two or three forecast apps before committing an evening and trust none of them alone. Two forums describe this in the users' own words (BAA 2024 and 2025; Talk Photography 2017). Nightwatch already reads Apple Weather as its primary cloud source on a signed build. v0.5 fetches Open-Meteo alongside it as a second opinion and says, in one line, whether the two agree about tonight. The cross-check then happens inside the alert instead of across three apps.

The first side-by-side at Home (24 September 2026) had the two sources calling opposite halves of the night clear, which is exactly the case this line flags.

Success criteria:

1. On a signed build, each patrol fetches Open-Meteo for the active site as well as Apple Weather. The popover shows one agreement line for tonight, and the heads-up and window-opening notifications carry the same words.
2. The line reads one of six things (§4), from forecast values alone. Nothing is logged, and nothing outlives the current forecast cache.
3. An opt-in setting, "Alert only when Open-Meteo agrees", holds back the heads-up and window-opening alerts when Open-Meteo would not itself meet the go rule inside the window.
4. Unsigned builds, which already run on Open-Meteo, are unchanged. There is no second opinion to show, and the line is hidden.
5. The Command Line Tools build keeps working, and every rule is tested in SkyCore.

## 2. Decisions

| Topic | Decision |
|---|---|
| Which source is primary | Apple Weather, as today (owner, 24 September 2026). Open-Meteo is the second opinion and never drives the verdict, the score or the bars |
| Unsigned builds | No second opinion. 7Timer's cloud field is 3-hourly and in coarse bins, so comparing it would mostly flag rounding. The line stays hidden |
| Dark sites | Home or active site only. The eight dark-site forecasts keep one source each, so the extra calls stay at one per patrol |
| Logging | None. The owner's objection stands: the second opinion lives in `forecast.json` beside the primary, and each patrol replaces both. The synthesis's challenge noted that divergence needs forecast values only, with no outcome log |
| What "agree" means | The same go rule applied to both sources, hour by hour: an hour is clear when cloud is at or under the rule's limit (default 25%) |
| Alerts | The heads-up and the nudge before the window carry the line. The stand-down and the tomorrow preview do not |
| Bright nights | The line compares cloud only, inside the bright window. No bright clear run is suggested from the second source, because the bright rule also needs a target at 15° |
| Wording | The same in both wording modes. No Discworld copy |

## 3. Data

### 3.1 Fetching (SkyCore, `ForecastService.fetch`)

When the primary provider answers with hours, also fetch `OpenMeteo.url(...)` for the same site and 3 days, and parse it with `OpenMeteo.parse`. Keep only each hour's time and total cloud. A failed or empty second fetch leaves the second opinion nil and never fails the forecast. When the primary fails and Open-Meteo is already the main source, the second opinion is nil.

`Forecast` gains `secondOpinion: SecondOpinion?`, where `SecondOpinion { source: String, hours: [HourlyCloud] }` and `HourlyCloud { time: Date, cloudTotal: Int }`. The field is optional, so a 0.4 `forecast.json` decodes unchanged.

### 3.2 Assessing (SkyCore, new `Agreement.swift`)

`Planner.agreement(plan: NightPlan, second: SecondOpinion?, rule: GoRule) -> Agreement?` returns nil when there is no second opinion, no darkness, or the second source lacks any hour the comparison needs. It considers the plan's dark hours only (nautical on a bright plan).

- **With a primary window W**, it looks at the second source's hours overlapping W:
  - all clear: `.agree`
  - a clear run of the rule's minimum length inside W:
    - cloud after that run has started: `.cloudFrom(the first such hour, clamped into W)`
    - cloud only before it: `.clearFrom(the run's start)`
  - no such run inside W, but one elsewhere in darkness: `.clearRun(its start, end)`
  - no clear run anywhere tonight: `.noWindow`
- **With no primary window**, it applies `Planner.windows` to the second source over darkness under the same rule:
  - none: `.agreeNoWindow`
  - one or more: `.clearRun(longest start, end)`
  - on a bright plan, this case returns nil

Amended 25 September 2026 at the Task 2 review. Reporting the first cloudy hour anywhere in W read "cloud from 20:00" when Open-Meteo merely cleared an hour later. "No clear window" was also shown when Open-Meteo had a clear run outside W.

`NightPlan` gains `agreement: Agreement?`, computed in `Planner.plan` from `forecast.secondOpinion`, like `limiting` in v0.4. `Agreement` is a Codable enum.

`Planner.agreementHolds(_:)` is false for `.noWindow` and `.clearRun`, where Open-Meteo is not clear enough inside the window, and true otherwise, including when there is no second opinion. The opt-in setting uses it.

## 4. The line

| Agreement | Popover and notification text | Mark |
|---|---|---|
| `.agree` | "Open-Meteo agrees" | a small tick, text.secondary |
| `.cloudFrom(t)` | "Open-Meteo sees cloud from 23:00" | amber dot |
| `.clearFrom(t)` | "Open-Meteo sees it clear from 21:00" | amber dot |
| `.noWindow` | "Open-Meteo sees no clear window" | amber dot |
| `.agreeNoWindow` | "Open-Meteo agrees: no clear window" | a small tick |
| `.clearRun(a, b)` | "Open-Meteo has a clear run 23:00–02:00" | amber dot |
| nil | hidden | none |

In the popover the line sits under the "Held back by" line in the headline block (v0.4 §5.1). It uses the same 10 pt text.secondary, so red stays for clear sky only. In notifications it is appended to the body as a sentence: "… NGC 7000 well placed. Open-Meteo agrees."

Screen readers hear the same sentence.

## 5. Settings

Alerts gains a toggle, "Alert only when Open-Meteo agrees", default off. It is stored as `AlertSettings.requireAgreement` and decoded leniently, so a missing key reads as false. When it is on and `Planner.agreementHolds` is false (`.noWindow` or `.clearRun`), `AlertEngine.step` sends neither the heads-up nor the nudge, and records nothing, so the alert can still fire later if a new patrol agrees. The toggle is disabled, with the note "Needs Apple Weather (signed build)", when the forecast has no second opinion.

## 6. Tests

SkyCore:
- the fetch fills `secondOpinion` when the primary answers
- it leaves `secondOpinion` nil when the primary fails, and when the second fetch fails
- all six agreement cases, plus nil for missing hours and nil on a bright plan without a window
- the `.cloudFrom` time is clamped to the window start when the first hour straddles it
- `agreementHolds`
- the alert engine holds back the heads-up with `requireAgreement` on and `.noWindow`, and sends it once a later patrol agrees
- a 0.4 `forecast.json` and a 0.4 `AlertSettings` both decode
- notification body wording
